# Prisma Workflow - OSS Database Rules

## Quick Reference

- **Schema changes**: Edit `prisma/schema.prisma` → run `bun run db:migrate dev` (migrates DB + generates client)
- **Pull changes from git**: Run `bun install` (postinstall hook auto-generates client) or manually `bun run db:generate`
- **Out of sync?**: Run `bun run db:generate` to regenerate `generated/` files
- **Test DB**: Use `TEST_DATABASE_URL` env var with separate test database
- **Switch target**: Set `DB_TARGET=local|neon|prisma-postgres` or `bun run db:migrate -- --env neon`

## Database targets

| Target | `DB_TARGET` | Prefixed vars |
|--------|-------------|---------------|
| Local Docker | `local` | `LOCAL_DATABASE_URL`, `LOCAL_DIRECT_DATABASE_URL` |
| Neon | `neon` | `NEON_DATABASE_URL`, `NEON_DIRECT_DATABASE_URL` |
| Prisma Postgres | `prisma-postgres` | `PRISMA_POSTGRES_DATABASE_URL`, `PRISMA_POSTGRES_DIRECT_DATABASE_URL` |
| Unprefixed (legacy) | `auto` or unset | `DATABASE_URL`, `DIRECT_DATABASE_URL` |

Never invent connection strings. Paste real URLs from Neon dashboard or Prisma Console Connect tab into `.env` / `.env.local` only.

## Key Files

| File | Purpose |
|------|---------|
| `prisma/schema.prisma` | Database schema (models, enums, relations) |
| `prisma/migrations/` | SQL migration files (auto-generated by CLI) |
| `prisma.config.ts` | Prisma CLI config; resolves URLs via `lib/databaseEnv.js` |
| `lib/databaseEnv.js` | Target switching, provider detection, URL redaction |
| `generated/` | Auto-generated Prisma client (gitignored, regenerated on `bun install`) |
| `lib/prisma.js` | Runtime client wrapper; Neon vs pg adapter selection |

## Adapter matrix

| Provider | Host / pattern | Runtime adapter |
|----------|----------------|-----------------|
| Neon | `.neon.tech` | `@prisma/adapter-neon` |
| Prisma Postgres | `db.prisma.io`, `prisma-data.net` | `@prisma/adapter-pg` |
| Local Docker | `localhost`, `127.0.0.1`, `database` | `@prisma/adapter-pg` |

Migrations always use direct `postgres://` URLs via `DIRECT_DATABASE_URL` (or target-prefixed `*_DIRECT_DATABASE_URL`). `prisma://` Accelerate URLs are runtime-only.

## Setup & First Run

### Clone or schema pull

```bash
bun install              # postinstall runs: bun run db:generate
docker compose up -d database  # start Postgres
bun run db:migrate:deploy      # apply migrations
bun run db:seed                # optional: sample data
bun run dev                    # start Next.js app
```

### Environment

| Variable | Use | Example |
|----------|-----|---------|
| `DB_TARGET` | Active target | `local`, `neon`, `prisma-postgres`, `auto` |
| `DATABASE_URL` | App runtime (auto mode) | `postgres://postgres@localhost:5432/oss` |
| `DIRECT_DATABASE_URL` | Prisma CLI (auto mode) | same as DATABASE_URL for local dev |
| `SHADOW_DATABASE_URL` | Shadow DB for migrations (optional) | `postgres://postgres@localhost:5432/oss_shadow` |
| `TEST_DATABASE_URL` | Test runs | `postgres://postgres@localhost:5432/oss_test` |

**Local dev**: `DB_TARGET=local` or leave `auto` with Docker URLs in `DATABASE_URL`.
**Neon**: `DB_TARGET=neon` + `NEON_*` vars, or `auto` with unprefixed Neon URLs.
**Prisma Postgres**: `DB_TARGET=prisma-postgres` + `PRISMA_POSTGRES_*` from Console Connect tab.

## Making Schema Changes

### 1. Edit schema

```bash
# Edit the schema file
vim prisma/schema.prisma
```

### 2. Create and apply migration

```bash
# This creates the migration file AND regenerates the client
bun run db:migrate dev
# Or, if running migrations on production:
bun run db:migrate:deploy  # Run pending migrations (no client regen here)
bun run db:generate         # Regenerate client after deploy if needed
# Specific remote target:
bun run db:migrate -- --env prisma-postgres
```

### 3. Git workflow

```bash
git add prisma/schema.prisma prisma/migrations/
git commit -m "feat: add new table XYZ"
git push
```

### 4. Teammate pulls changes

```bash
git pull
bun install              # postinstall runs: bun run db:generate
# Database is auto-migrated if using dev server, or manually:
bun run db:migrate:deploy
```

## Common Patterns

### Add a new model

```prisma
model BlogPost {
  id        String   @id @default(cuid())
  title     String
  content   String
  published Boolean  @default(false)
  userId    String
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([userId])
}
```

Then: `bun run db:migrate dev` (name it `add_blog_posts`)

### Query with relation

```javascript
// After migration, Prisma client includes BlogPost model
const post = await prisma.blogPost.findUnique({
  where: { id: 'some-id' },
  include: { user: true } // loads related User
});
```

### Soft delete pattern

```prisma
model Project {
  // ... fields ...
  deletedAt DateTime? // null = active, set timestamp to soft-delete
}
```

Query active records:

```javascript
const projects = await prisma.project.findMany({
  where: { deletedAt: null }
});
```

## Troubleshooting

### Build error: "Can't resolve '../generated/client.js'"

**Cause**: Prisma client not generated after schema changes.

**Fix**:
```bash
bun run db:generate
```

Then rebuild.

### "Unexpected token" or TypeScript errors in generated files

**Cause**: `generated/` files are out of sync (old version after schema change).

**Fix**:
```bash
rm -rf generated/
bun run db:generate
```

### Migration conflicts

**Cause**: Two developers created overlapping migrations.

**Fix**:
```bash
# Merge the migration files manually, or reset (dev only):
bun run db:migrate reset  # drops all tables, reapplies migrations
```

### "PrismaClientValidationError" or schema errors at runtime

**Cause**: Stale or missing generated client.

**Fix**:
```bash
bun run db:generate
bun run dev  # restart dev server
```

### Wrong database after switching targets

**Cause**: `DB_TARGET` set but prefixed URLs missing.

**Fix**: Verify `NEON_*` or `PRISMA_POSTGRES_*` vars in `.env`, or use `auto` with unprefixed `DATABASE_URL`.

## Best Practices

- ✅ Always run migrations through Prisma CLI (`bun run db:migrate dev`), never raw SQL
- ✅ Commit `prisma/schema.prisma` and `prisma/migrations/` to git
- ✅ Never commit `generated/` — it's gitignored and regenerated on `bun install`
- ✅ Never commit or log full connection strings
- ✅ Keep schema and code in sync; if you see Prisma client errors, regenerate immediately
- ✅ Use `SHADOW_DATABASE_URL` for complex migrations in development
- ✅ Test queries with sample data after migrations (use `bun run db:seed`)
- ✅ Use `.gitignore` correctly: `generated/`, `.env.local`, `node_modules/`
